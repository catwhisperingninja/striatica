# Striatica v6.2.2 — Implementation Control

**Status:** PROVISIONAL — DAG node list is seeded from the Amp 2026-08-28 adversarial review and must be reconciled against v6.2.2 when it lands (see §12).
**Created:** 2026-08-31
**Owns:** how work is dispatched, evidenced, and promoted.
**Does not own:** requirements, scientific claims, or acceptance criteria. `v6.2.2-plan.md` owns those.

---

## 1. Why this document exists

The v6.x loop has been: write plan → adversarial review → rewrite plan → adversarial review. Three cycles, no code promoted. The diagnosis is not that the plans are too long. It is that **the plans record conclusions without recording how each conclusion was reached**, so every fact silently upgrades as it is copied into the next version. "Loader supports transcoders" becomes "migration complete." "Path count unchanged" becomes "zero drift verified." "One run plus CodeRabbit" becomes "verified 2×."

Splitting the plan into sections does not fix this — it multiplies the number of places one fact has to be right. The claims ledger is already a separate document and is the single worst artifact in the review (eleven defects, including an amendment table overriding a stale base table).

This document fixes it structurally:

- Status becomes **data**, not prose (§9).
- Vocabulary is **closed** (§4, §5).
- Work is dispatched as **bounded tickets** with pre-declared acceptance tests (§7).
- Nothing self-promotes; promotion requires **independent review** (§3, §8).
- Review findings **never become implementation prompts** (§10).

| **Implementer** (Claude/agent, one ticket at a time) | Write code and tests in permitted files; run tests; report results as data | Promote evidence state; declare "verified"; generate production data; touch files outside the ticket; act on the master plan |
| **Reviewer** (independent — human, or a fresh agent with no implementation context) | Promote evidence state; reject; open new DAG nodes | Implement the thing under review |
| **Adversarial reviewer** (Amp, DeepSeek) | Produce findings against the acceptance oracle | Direct implementation; findings route through §10 |
| **Principal** (Laura) | Approve scientific claim promotion, production-data regeneration, visual sign-off, tags/pushes, publication | — |

**Standing constraints (not tickets):**

- PR #8 does not merge. The private findings document does not go under tracked `dashboards/`.
- No gate run writes to `frontend/public/data/`. Test outputs go to disposable paths.
- No tag, branch push, authenticated Neuronpedia call, or data regeneration follows from any ticket completing.
- `img/**` is private and gitignored. Nothing in a tracked file may reference it as evidence.

## 3. Promotion ladder

```
PROPOSED → CODE_INSPECTED → EXECUTED_ONCE → REPRODUCED_2X → VERIFIED
```

Each arrow requires an **independent review of the exact commit SHA**. No state is self-declared by the implementer.

| State | Requires |
|---|---|
| `PROPOSED` | A DAG node exists with an outcome and acceptance tests written **before** work starts |
| `CODE_INSPECTED` | Reviewer read the diff at a named SHA; logic is correct on inspection. No execution claim. |
| `EXECUTED_ONCE` | Positive **and** negative acceptance tests ran; exit status and output hashes recorded; one environment |
| `REPRODUCED_2X` | Two independently provisioned fresh environments, same SHA + lock hash + image digest + input hashes + command set. Two invocations in one mutable environment do **not** qualify. |
| `VERIFIED` | `REPRODUCED_2X` **and** static review clean on that SHA **and** principal sign-off where the node touches a scientific claim or public surface |

**Static review is not an execution.** CodeRabbit is a separate evidence class. Local run + CodeRabbit = one execution and one review, never `REPRODUCED_2X`.

---

## 4. Evidence classes (closed enum)

Every load-bearing status row carries exactly one:

```
code-inspected
static-review
keyless-api-observation
authenticated-capability-test
executed-once
reproduced-2x
```

Anything not on this list is not an evidence class. "Confirmed," "checked," "looks right" are rejected by the checker.

## 5. Banned vocabulary

These words may not appear in a status field, a ticket outcome, or an evidence record:

> `verified` · `fixed` · `complete` · `done` · `working` · `reproducible` · `zero drift` · `enabled` · `passing` · `clean`

They are permitted only in prose that immediately cites a row ID and an evidence class. The checker (§11) greps for them.

**Rationale, with receipts:** every one of the review's P0 findings is an instance of one of these words carrying more weight than its evidence. F-05 (`verified 2×`), F-06 (`reproducible`), F-08 (`zero drift`), A.7 (`complete`).

## 7. Ticket schema

One ticket = one node or node-slice. **1–3 implementation files plus their tests.** If it needs more, split the node.

```markdown
## TICKET T-NNN · <node-id> · <short outcome>

BASE SHA:      <40-hex>            # exact; not "main", not "latest"
BASE STATE:    clean | <describe>
OUTCOME:       <one sentence, one observable change>

PERMITTED FILES:
  - path/one.py
  - path/one_test.py
NON-GOALS (do not touch, do not fix, do not refactor):
  - <named adjacent thing that is tempting>
  - <named adjacent thing that is tempting>

REQUIRED POSITIVE TESTS:
  - <test name> — asserts <exact condition>
REQUIRED NEGATIVE TESTS:
  - <test name> — asserts the gate FAILS when <corruption>
    (a node with no negative test cannot leave CODE_INSPECTED)

EMBEDDED CONTEXT (everything needed; do not read the master plan):
  <the 3–10 lines of fact this ticket depends on, quoted inline>

RETURN EXACTLY:
  - local commit SHA
  - diff summary (files, +/- lines)
  - full test output (verbatim, including exit status)
  - unresolved facts / things found but not fixed
  - evidence class claimed: code-inspected | executed-once
  DO NOT report: "verified", "fixed", "complete", "working", "passing"
```

**Embedded context is mandatory.** The implementer must never reconstruct the master plan, and must never receive the adversarial review as a prompt. If a ticket cannot be written without attaching a 1,000-line document, the node is too big.

## 8. Mandatory review points

1. **Before dispatch** — acceptance tests exist and are written down. A node whose tests are written after the code is not reviewable.
2. **Immediately after return, before any dependent ticket starts** — reviewer reads that exact commit. Dependent work on an unreviewed parent is forbidden; that is how the v6.x drift happened.
3. **At each promotion** — independent reviewer, not the implementer.
4. **Before any `REPRODUCED_2X` claim** — the two environment manifests are compared field by field.
5. **Before any public surface changes** — principal sign-off (Lane C nodes touching README/ERRATA/paper).

## 9. Status / evidence table

One machine-readable file: `status/nodes.yaml`. Append-only on `history`. The prose in any plan document cites row IDs; it does not restate status.

```yaml
- nodeId: A1a
  title: dim-contract-schema
  lane: A
  dependsOn: [A0a]
  paperDisposition: null          # Lane C only: RETAIN|REVISE|RETRACT|ADD|HOLD
  evidenceMaturity: PROPOSED      # PROPOSED|CODE_INSPECTED|EXECUTED_ONCE|REPRODUCED_2X|VERIFIED
  evidenceClass: null             # closed enum, §4
  basisRef: null                  # basis.json hash from A0a
  commitSha: null
  testEvidence: []                # {name, exitStatus, outputHash}
  reviewedBy: null
  reviewedSha: null
  openQuestions:
    - "Is [0,100] a method-specific bound or dataset policy? Not mathematics."
  supersedes: null
  history:
    - {date: 2026-08-31, change: created, by: implementation-control, note: "seeded from Amp 2026-08-28 F-04"}
```

Rules the checker enforces:

- `evidenceMaturity ≥ EXECUTED_ONCE` requires non-null `commitSha`, `basisRef`, and ≥1 positive **and** ≥1 negative entry in `testEvidence`.
- `evidenceMaturity ≥ REPRODUCED_2X` requires two `testEvidence` sets with matching `basisRef` and distinct environment IDs.
- `VERIFIED` requires `reviewedBy` ≠ implementer and `reviewedSha == commitSha`.
- A row is never edited in place. Corrections append to `history` and set `supersedes`.

## 10. Review-finding intake (how DeepSeek's reviews route in)

**No adversarial review is ever handed to an implementer.** A review is an *acceptance oracle*. Every finding routes to exactly one of three destinations:

| Finding type | Destination |
|---|---|
| Names a behaviour the code should have and doesn't | **New DAG node**, or a new acceptance test on an existing node |
| Names a claim that overstates its evidence | **Lane C claims-ledger row** — disposition + maturity downgrade |
| Names a fact that is stale or wrong | **Lane C fact node** (like C4) with a re-derivation requirement |

DeepSeek's two-part split maps cleanly:

- **Science / evidence part** → Lane C rows (C1, C3) + acceptance oracle for Lane B (B3 method validation).
- **Code functions part** → Lane A and B nodes + acceptance tests.

**Intake procedure:** for each finding, append one row to `status/findings.yaml` with `{findingId, source, destination, nodeId|claimId, dispositioned: bool}`. A review is *ingested* when every finding has a destination — not when it has been implemented. This is what stops a review from becoming a rewrite.

## 11. Checker

Read-only. Runs in a local pre-commit hook (fast feedback) and in CI (the enforceable control). Never edits, stages, tags, pushes, or regenerates.

Checks:

1. `nodes.yaml` / `findings.yaml` schema; unique IDs; no ID recycled.
2. `evidenceMaturity` and `evidenceClass` are members of the closed enums.
3. Promotion preconditions from §9 hold.
4. Every citation row carries source + section/quote + a not-supported-by note.
5. Banned vocabulary (§5) absent from status fields and tracked prose.
6. No tracked file references an `img/**` path as evidence.
7. Every Dockerfile installs from the committed lock and never runs `poetry lock`.
8. Emits IDs and pass/fail only — never semantic content, labels, or matched payloads.

Build this at **C6**, early. It is what makes the doctrine self-enforcing instead of another document that rots.
