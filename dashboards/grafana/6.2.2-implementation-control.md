## 1. Normative language and authority

`MUST`, `MUST NOT`, `REQUIRED`, `SHALL`, and `SHALL NOT` are normative. `SHOULD`
expresses the default and requires written evidence to override.

Authority, highest first:

1. an explicit current user decision;
2. repository safety and privacy doctrine in `CLAUDE.md`;
3. this exact ratified specification and its accepted change records;
4. machine status/evidence records generated under this specification;
5. source reviews and historical plans as evidence, not as executable orders.

An agent SHALL stop and return a blocker when a lower authority conflicts with a
higher one. An implementer SHALL NOT resolve a scientific or publication
decision by choosing whichever branch makes its ticket easiest.

### 1.2 Fixed safety invariants

Every ticket inherits these without repeating them:

- Semantic labels SHALL NOT be committed, pushed, baked into images, logged,
  copied into evidence, or persisted to a version-controllable file.
- No synthetic application dataset, placeholder circuit, or hardcoded feature
  index may substitute for real data. Synthetic known-geometry controls are
  allowed only for method validation in `audit/`.
- No file under `frontend/public/data/` may be regenerated without explicit
  `G-DATA`; visual acceptance requires separate `G-VISUAL`.
- Dockerfiles and CI SHALL consume the committed `poetry.lock` and SHALL NOT run
  `poetry lock`.
- The CPU image is the canonical execution path. GPU support is a separate,
  later compatibility node.
- The Euclidicity/TDA audit remains isolated from the main Poetry environment.
- Tracked public-safe gap maps, neutral DAG status, ERRATA, and release evidence
  are permitted credibility artifacts. Designated public data and projection
  fields SHALL contain no private strategy, private claim prose, semantic
  labels, or locator into ignored evidence. Doctrine and control specifications
  may name private path conventions when necessary to define and enforce the
  boundary; they SHALL NOT reproduce private evidence payloads.
- No push, PR mutation, merge, branch deletion, tag, package publication,
  deployment, or release occurs without explicit `G-RELEASE` or the narrower
  named principal gate.
- Passing numerical tests does not establish visual correctness or scientific
  validity.

## 3. Roles and separation of authority

### 3.1 Principal

The user/principal alone may:

- ratify or amend this specification;
- choose VGT, comparator, Euclidicity, paper-disposition, data-regeneration,
  visual, checkpoint, and release gates;
- authorize shared or external state changes;
- accept a residual scientific uncertainty for publication.

### 3.2 Controller/integrator

The controller:

- generates tickets from accepted nodes;
- confirms dispatchability and file-set non-overlap;
- assigns implementer and independent reviewer;
- integrates only accepted local commits;
- updates the four-field current-state row in the same reviewed commit as the
  controlled transition; Git retains its history;
- never silently changes node requirements or scientific outcomes.

### 3.3 Implementer

The implementer:

- works only on the exact ticket basis and permitted files;
- runs the specified positive/adverse checks;
- records commands, exit codes, artifacts, hashes, and deviations;
- stops if an unpermitted file or unresolved decision is needed;
- may create a local commit when the ticket requires an exact review basis;
- cannot accept the node or classify its evidence as sufficient.

### 3.4 Independent reviewer

The reviewer:

- did not implement the node;
- reads the requirement and acceptance IDs before the diff;
- inspects the exact implementation basis and dirty state;
- checks both intended behavior and adverse cases;
- records accepted, changes-requested, blocked, or inconclusive with evidence;
- never fixes the implementation under review in the same review role.

### 3.5 Scientific/source reviewer

A scientific/source reviewer checks method, citation entailment, artifacts,
falsifiers, and contrary evidence. Code review cannot substitute for this role.

## 4. Lifecycle, evidence, and records

### 4.1 Node lifecycle

```text
PROPOSED → READY → IN_PROGRESS → IMPLEMENTED → ACCEPTED
                       │              │
                       └→ BLOCKED     └→ CHANGES_REQUESTED
```

`SUPERSEDED` is also a state. `ACCEPTED` is justified by the node's acceptance/
evidence requirements and independent review; the implementer cannot set it. The
tracked state diff and Git commit are the transition record. Do not maintain a
second event-history system inside Git.

### 4.2 Evidence types

Evidence is a set of records:

- `staticInspection`
- `testExecution`
- `independentExecution`
- `artifactRemeasurement`
- `sourceVerification`
- `visualReview`
- `principalApproval`

Execution and inspection are orthogonal. Deterministic repetitions do not show
method correctness. A screenshot illustrates a state but does not prove an
interaction that was not exercised.

### 4.3 Tracked control layout

Node `K-SCHEMA-01` SHALL establish the control schemas and the canonical DAG and
state instances. `D-PUBLIC-MANIFEST-01` creates the two public projection
instances after their evidence-producing dependencies are accepted:

```text
control/dag.yaml                 canonical node and edge definitions
control/state.yaml               four-field current state for every node/gate
control/schemas/*.json           DAG/state/public-projection schemas
control/public-claims.yaml       public-safe claim projection
control/release-manifest.yaml    exact-candidate release evidence
```

Private records remain ignored:

```text
img/correction/v6_plans/6.2-claims-ledger.md
img/correction/v6_plans/6.2-private-changelog.md
img/correction/v6_plans/evidence/**
```

No designated public projection field may contain private prose or private
paths. Control specifications may name private path conventions to define the
boundary. A neutral private artifact ID and content hash may be projected only
when disclosure is safe and approved.

### 4.4 Static DAG and four-field state schemas

`control/dag.yaml` holds definitions that change only through §13:

```yaml
id: A-SCHEMA-01
title: Versioned metric/provenance contract
requirementIds: [R-DATA-001, R-DATA-002, R-DATA-003]
acceptanceIds: [A-SCHEMA-01-AC1, A-SCHEMA-01-AC2]
permittedFiles: []
nonGoals: []
dependencies:
  - nodeId: B-VGT-APPLY-01
    requiredParentState: ACCEPTED
principalGateIds: []
requiredEvidenceTypes: [staticInspection, testExecution]
```

`control/state.yaml` contains one row per DAG node and `G-*` gate, with exactly
four fields in schema version 1:

```yaml
A-SCHEMA-01:
  state: PROPOSED
  sha: null
  evidence: {}
  note: ""
```

- `state` is one lifecycle value from §4.1.
- `sha` is the exact reviewed result: `git:<40-hex>` for a clean tracked commit
  or `sha256:<64-hex>` for a private artifact. It is null before an implemented
  result exists. Dirty work cannot become `IMPLEMENTED` or `ACCEPTED`.
- `evidence` maps each required evidence type to one resolvable public locator
  or neutral hash, or a short list when the node requires repetitions. It is not
  a nested copy of command output.
- `note` is one concise human handoff/blocker string. It names open finding IDs,
  gate conditions, or a superseding node when applicable; it does not carry a
  history array, paper disposition, test transcript, or open-question database.

Static requirements, dependencies, acceptance, file scope, and gates remain in
`dag.yaml`; implementer/reviewer identity and dispatch basis remain in the
generated ticket and review artifact. This simplification removes duplicate
state machinery without removing the controls needed to review a node.

### 4.5 Evidence pointers and finding records

Evidence stays typed but is referenced, not copied into a bespoke ledger:

```yaml
A-SCHEMA-01:
  state: IMPLEMENTED
  sha: git:0123456789abcdef0123456789abcdef01234567
  evidence:
    testExecution: "ci-run:<public-run-id>#control-tests"
    staticInspection: "sha256:<scrubbed-review-hash>"
  note: "awaiting independent acceptance review"
```

Raw logs are not committed. A referenced execution record states the exact
basis/environment, command, exit code, result, output hash, and what differed in
an independent repetition. A referenced review identifies reviewer and exact
basis. Private records are named only by neutral ID/hash in public state.

Findings live in the source adjudication tables in §8 and later change records
in §13. Each has source/finding ID, adjudication, rationale, destinations, and
evidence. An unresolved finding ID is repeated in each affected node's `note`.
There is no separate `findings.yaml`; adding a fifth state field requires an
observed operational need and a §13 schema change.

A finding is not resolved merely because it has a destination.

## 7. Node specifications

Every listed dependency requires parent state `ACCEPTED`. “Permitted files” are
the maximum initial scope; needing another file is a blocker/change request, not
implicit permission. Tests adjacent to a permitted implementation file are
allowed only when explicitly named below.

Every node inherits these explicit non-goals: no outcome assigned to another
node, no file outside its permitted set, no production-data regeneration, no
principal decision, and no shared/external state mutation. A generated ticket
MUST repeat these and add any node-specific exclusions.

Acceptance IDs are deterministic. An already-labelled criterion keeps its label.
Otherwise, each ordered bullet under **Acceptance** is `<NODE-ID>-AC1`, `-AC2`,
and so on; when **Acceptance** is one paragraph, the whole conjunction is
`<NODE-ID>-AC1`. The machine DAG MUST materialize these IDs without splitting or
weakening a conjunction.


An implementer SHALL NOT receive the 1,000-line reviews as its operative prompt.
The ticket embeds only the exact context required for its node and links neutral
source IDs for traceability.

### 9.2 Dispatchability algorithm

A node is `READY` only if:

1. G-RATIFY is satisfied;
2. all dependencies are `ACCEPTED` at their recorded exact refs;
3. all node principal gates are satisfied;
4. every requirement/acceptance ID resolves;
5. implementer and independent reviewer are assigned and differ;
6. permitted files do not overlap another active ticket;
7. basis is clean or its exact approved dirty state is recorded;
8. required inputs exist and hashes match;
9. no unresolved critical/major finding targets the node;
10. controller generates and validates the ticket.

### 9.3 Failure behavior

- Test failure: record evidence and set `CHANGES_REQUESTED` or `BLOCKED`; do not
  weaken acceptance.
- New required file: stop and request a scope change.
- Contrary scientific result: record it; do not tune thresholds until green.
- Dependency change: invalidate descendants whose accepted basis includes it.
- Integration conflict: reopen affected parent nodes; integrator does not make
  unreviewed semantic fixes.
- Environment failure: distinguish install/environment from product failure;
  never report the target check as passed.

## 10. Parallel branches, worktrees, and integration

1. Each implementation ticket starts from its exact accepted dependency basis in
   a dedicated branch/worktree or isolated orb checkout.
2. The controller records branch/worktree/executor identity. A branch name is
   local implementation metadata, not authorization to push.
3. No two active tickets own overlapping paths. If overlap is unavoidable, the
   nodes run serially.
4. Implementer creates one reviewable local commit per coherent node outcome.
5. Reviewer inspects/tests that exact commit and dirty state.
6. Integrator cherry-picks or rebases only `ACCEPTED` commits in topological
   order onto one local candidate.
7. Any conflict resolution is a new change requiring affected-node review.
8. Integrated tests run at the exact candidate. Isolated acceptance does not
   imply integration acceptance.
9. No agent pushes, opens/updates/closes a PR, merges, tags, deletes a branch,
   or releases without the precise principal authorization.

Amp orb and local Claude workspaces do not share uncommitted files implicitly.
Tickets SHALL state transfer/commit mechanics and distinguish local `main` from
`origin/main`.

## 11. Checker, hook, and CI boundaries

### 11.1 Public tracked checks

CI may enforce:

- DAG/state schema, one-to-one row, reference, and cycle integrity;
- accepted-parent/gate states, SHA forms, and required evidence-pointer
  presence;
- test/build/lint commands;
- public manifest/evidence locators;
- changelog policy for controlled changes;
- Docker lock-consumption and no-lock-regeneration policy;
- public artifact semantic-label safety;
- absence of private paths/content in designated public fields.

CI SHALL NOT require ignored private files or reject all textual mentions of
`img/**`; `.gitignore` and doctrine legitimately name the boundary. Reviewer
separation is confirmed from the generated ticket and review artifact by the
controller; it is not pretended from a self-declared state field.

### 11.2 Local private guard

The local guard may validate private ledger/changelog schemas, content hashes,
requirement coverage, accidental tracked status, and safe public projection. It
shall not copy private text into CI output.

### 11.3 What automation cannot certify

Automation cannot determine whether:

- a citation entails a claim;
- an estimator measures the intended construct;
- contrary evidence invalidates a paper interpretation;
- two executions are scientifically independent;
- a visualization is correct to a human.

Independent review and principal gates remain mandatory. There is no repository-
wide banned-word grep. Scoped negative checks may reject exact retired claim
phrases on designated claim-bearing surfaces, and an optional pre-commit hook
may run those checks for fast feedback; required CI remains the shared
enforcement.
